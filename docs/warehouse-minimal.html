Minimal warehouse: per-line sales, picked options, one dashboard

The scope agreed with the teacher, revised after the second review: the order is a header and its lines are the body, the fact is per line, and modifiers are options picked from a list. Built end to end so the owner can see revenue by channel, what sells, and what add-ons earn. Every number below comes from notebooks/warehouse_minimal.ipynb.

The design rules do not change with the scope. This is still a Kimball dimensional warehouse following MADT8102 chapter 5: _key surrogate keys, special-case rows (0 Not applicable, 1 Unknown, 2 Invalid) instead of NULL keys, a junk dimension for order status, degenerate order and line numbers, and facts compared by drilling across.

4 · Header and body: the fact is per line

The POS and every delivery app send an order as a header (who, when, which channel, commission, delivery fee) and lines, one per menu item. The warehouse keeps one sales fact, at the line:

  • Header attributes become keys on every line. Date, channel, customer and order status are the same for all lines of an order, so each line carries them.
  • Header money is allocated down. Commission and delivery fee are split across the order's lines in proportion to line gross (item plus picked options), rounded to the satang, with the remainder on the last line. On GF-201, 146.4 THB of commission becomes 113.70 on the 379 THB pepperoni and 32.70 on the 109 THB garlic bread.
  • The header itself is the degenerate order_number. An order count is COUNT(DISTINCT order_number).
  • Every load reconciles: allocated commission summed by order must equal the header's, or the load stops.

One grain for every sales measure: revenue, commission and net revenue roll up the same way by order, channel, day or item, with no header fact to join and nothing to double-count.

Options are picked, not typed

The POS screen shows each item's options from DIM_MODIFIER_OPTION (grouped as Cheese, Spice, Crust) and stores each tap as a row: order, line, option code, price charged. No free text reaches the warehouse. A code that is not on the list loads against row 2, Invalid, with an alert, so it is visible rather than lost.

Each is built only from the warehouse, excludes cancelled orders, and stores additive measures only. Ratios such as average order value are computed by the dashboard from the parts, so they stay correct by day, week or month.
