Warehouse ของโปรเจกต์: ทีมสร้างอะไร และใช้งานยังไง

warehouse ของโปรเจกต์นี้ ตั้งแต่ข้อมูลต้นทางที่ผ่าน staging แล้ว ไปจนถึง mart ที่เจ้าของร้าน รายการสั่งของ และโมเดลพยากรณ์อ่าน ครอบคลุม dimension, fact table และ mart ทุกตัว ข้อตกลงที่ทุกตารางต้องทำตาม และการโหลดข้อมูลในแต่ละคืน

ชั้นข้อมูล stg → dw → mart โมเดล Star · dimension 10 · fact 13 Mart 6 ตัว รอบอัปเดต ทุกคืน 03:00 core · 03:30 mart

English version: warehouse-design.html

1 · warehouse คืออะไร และทำไมโปรเจกต์ต้องมี

warehouse คือ zone Trusted และ Refined ของ data lake ของเรา (data-flow.th.html): star schema หนึ่งชุดที่มี conformed dimension กับ fact table และมี mart หนึ่งตัวต่อหนึ่งคำถามทางธุรกิจ ที่นี่เป็นที่เดียวที่กฎธุรกิจอยู่ แดชบอร์ด รายการสั่งของ และโมเดลพยากรณ์อ่านจากที่นี่ ไม่อ่านจากระบบต้นทางเลย

เหตุผลเห็นได้ชัดที่สุดจากคำถามเดียว: วันศุกร์ได้รายได้สุทธิแต่ละช่องทางเท่าไร?

ถามจาก source: 30 บรรทัด

query ต้องแบกกฎ 6 ข้อไว้เอง: รวมข้อมูลสองหน้าตา, แปลง UTC เป็นเวลากรุงเทพ, วันทำการ 10:00–02:00, ใช้ MAX ไม่ใช่ SUM กับค่าคอมมิชชันที่ Grab ซ้ำทุกแถว, parse ราคา modifier ออกจาก text และแปลง QR → QR_DINEIN แถม POS ยังเขียนทับราคาของสัปดาห์ก่อนไปแล้วด้วย

ถามจาก warehouse: 7 บรรทัด

SELECT channel_code,
       SUM(net_revenue_thb)
FROM dw.fct_order
JOIN dw.dim_channel USING (channel_sk)
JOIN dw.dim_date USING (date_sk)
WHERE calendar_date = '2026-09-04'
GROUP BY channel_code

ได้คำตอบเดียวกัน (Grab 599.9, โทรศัพท์ 408.0, QR 808.0 บาท จากข้อมูลต้นแบบ) กฎทั้งหมดถูกใช้ไปครั้งเดียวตอนโหลด รายงานไหนก็คำนวณผิดไม่ได้

2 · ชั้นข้อมูล และใครอ่านอะไร

ชั้นเก็บอะไรสร้างเมื่อใครอ่าน
rawทุกเรคคอร์ดจากต้นทางตามที่มาถึง พร้อม source_system, ingest_ts, source_file ไม่มีการแก้ไขตอนนำเข้าpipeline เท่านั้น

กฎการเข้าถึง
แดชบอร์ดและเครื่องมือต่าง ๆ อ่านจาก mart เท่านั้น นักวิเคราะห์ query dw ได้เมื่อมีคำถามใหม่ นอกจาก pipeline แล้วไม่มีใครอ่าน raw หรือ stg คำถามไหนถูกถามทุกสัปดาห์ ให้ทำเป็น mart

6 · ข้อตกลงที่ทุกตารางต้องทำตาม

นี่คือกฎที่ทีมใช้กับทุกตารางใหม่ ตัวเลขมาจากต้นแบบใน notebooks/warehouse_design.ipynb ซึ่งตั้งใจทำให้แต่ละข้อพังเพื่อให้เห็นว่ามันปกป้องอะไร

ข้อตกลงปกป้องอะไร (ตัวเลขจากต้นแบบ)
บอก grain ก่อนทุกตารางมี grain ในประโยคเดียว เงินระดับออร์เดอร์ห้ามอยู่ในแถวระดับบรรทัด ถ้า join แล้ว sum คอมมิชชัน Grab วันศุกร์จะเป็น 403.5 แทน 257.1
snapshot ค่าที่เป็นนโยบายราคา ต้นทุน และตัวคูณ OT ถูกคัดลอกลง fact ณ ตอนที่เกิด ไม่อย่างนั้นการขึ้นราคาวันเสาร์จะเปลี่ยนรายได้ Pepperoni L วันศุกร์จาก 1,037 เป็น 1,047
list ต้องเป็นตารางห้ามมี list ในคอลัมน์ เก็บ modifier เป็นแถวทำให้ variance มอซซาเรลลาวันศุกร์เป็น −20 กรัม ถ้าเก็บเป็น text จะเป็น −100 กรัม
เก็บสิ่งที่บวกได้fact เก็บส่วนที่บวกได้ อัตราส่วนคำนวณตอน query ค่าที่เป็นระดับอย่างยอดนับสต็อกห้ามบวกข้ามเวลา ("คงเหลือ" 16.3 กิโล แต่ของจริง 5.2 กิโล)
FK หนึ่งตัวต่อแหล่งห้ามมีคอลัมน์อ้างอิงที่ใช้ร่วมกัน key แบบ polymorphic ทำให้การรับชีส 2 กิโลไป join กับพิซซ่าได้โดยไม่มี error
surrogate key, SCD2fact เก็บแต่ key ของ warehouse เมนู สูตร และพนักงานเก็บทุกเวอร์ชัน fact join กับเวอร์ชันที่ใช้ได้ในวันทำการของมัน
วันทำการครั้งเดียวdate_sk ถูกกำหนดตอนโหลด (10:00–02:00) query ปลายทางไม่ต้องคำนวณเวลาเองเลย

7 · การโหลดในแต่ละคืน

ด่านตรวจคุณภาพที่หยุดการโหลด (รายการเต็มอยู่ใน README §10):

  • business key ที่หา dimension ไม่เจอ (เช่นเมนูใหม่ของ Grab ที่ยังไม่มีใน BRG_CHANNEL_MENU_ITEM) จะถูกกักไว้พร้อมแจ้งเตือน รายได้ไม่หายไปแบบเงียบ ๆ
  • ส่วนลดระดับบรรทัดต้องรวมได้เท่ากับส่วนลดระดับออร์เดอร์ทุกใบ
  • การเคลื่อนไหวสต็อกแต่ละครั้งมี FK ต้นทางได้อย่างมากหนึ่งตัว และต้องตรงกับ movement_type
  • upsert ด้วย (channel_sk, external_order_id) โหลดไฟล์ export ซ้ำก็ไม่ทำให้รายได้เป็นสองเท่า
  • ประมวลผล 3 วันทำการล่าสุดใหม่ทุกคืน เพื่อเก็บออร์เดอร์ที่มาช้า
