1 · ทำ warehouse ไปเพื่ออะไร? ลองถามคำถามเดียว

เจ้าของร้านถามว่า วันศุกร์ได้รายได้สุทธิแต่ละช่องทางเท่าไร? สุทธิคือเงินที่ร้านได้จริงหลังหักค่าคอมมิชชันของแอปเดลิเวอรี เราตอบคำถามนี้สองครั้ง: ครั้งแรกถามจาก POS กับไฟล์ export ของ Grab ตรง ๆ ครั้งที่สองถามจาก warehouse

ถามจาก source: SQL 30 บรรทัด

query ต้องแบกกฎ 6 ข้อไว้เอง:

  1. รวมข้อมูลสองหน้าตาเข้าด้วยกัน (ตาราง POS กับ CSV ของ Grab)
  2. แปลงเวลา UTC ของ Grab เป็นเวลากรุงเทพ
  3. วันทำการ: ออร์เดอร์ก่อน 10:00 นับเป็นของเมื่อวาน
  4. Grab ซ้ำค่าคอมมิชชันทุกแถว ต้องใช้ MAX ไม่ใช่ SUM
  5. ราคาชีสเพิ่มซ่อนอยู่ในคอลัมน์ text ต้อง parse เอง
  6. POS เรียกว่า QR แต่ที่อื่นเรียก QR_DINEIN

ถามจาก warehouse: 7 บรรทัด

SELECT c.channel_code,
       SUM(o.net_revenue_thb)
FROM dw.fct_order o
JOIN dw.dim_channel c USING (channel_sk)
JOIN dw.dim_date d    USING (date_sk)
WHERE d.calendar_date = '2026-09-04'
GROUP BY ALL

ไม่มีกฎอยู่ข้างในเลย กฎทั้งหมดถูกใช้ไป ครั้งเดียว ตอนโหลดข้อมูล

GRAB857.0257.1599.9
PHONE408.00.0408.0

ทั้งสอง query ได้ตารางนี้เหมือนกัน ต่างกันตรงที่ฉบับ source จะถูกก็ต่อเมื่อนักวิเคราะห์ทุกคน แดชบอร์ดทุกอัน และโมเดลพยากรณ์ จำกฎทั้ง 6 ข้อได้และเขียนเหมือนกันทุกครั้ง ลืมข้อ 4 ค่าคอมมิชชันของ Grab จะเป็นสองเท่า ลืมข้อ 3 ออร์เดอร์ตอนตี 1:20 จะย้ายไปอยู่วันเสาร์

ปัญหาข้อที่ 7: ประวัติหายไปแล้ว
วันเสาร์เจ้าของร้านขึ้นราคา Pepperoni L จาก 329 เป็น 349 บาท แล้ว POS ก็เขียนทับราคาเดิมไป ตอนนี้ตารางเมนูมีแค่ 349 คำถาม "margin ก่อนขึ้นราคาเป็นเท่าไร" จะตอบจาก POS ไม่ได้อีกเลย ระบบหน้าร้านตอบว่า ตอนนี้อะไรจริง แต่งานวิเคราะห์ต้องการ ตอนนั้นอะไรจริง

2 · warehouse มีไว้ทำอะไร

เหตุผลสำหรับร้านพิซซ่าอยู่ตรงไหนในโมเดล
รวมข้อมูลห้าแหล่ง รูปแบบเดียว ออร์เดอร์จาก Grab กับจาก QR เป็นหนึ่งแถวใน FCT_ORDER เหมือนกันDIM_CHANNEL, BRG_CHANNEL_MENU_ITEM
นิยามครั้งเดียววันทำการ รายได้สุทธิ และชื่อช่องทาง ถูกคำนวณตอนโหลด ไม่ใช่ในทุกรายงานdate_sk คือวันทำการ, เก็บ net_revenue_thb ไว้เลย
เก็บประวัติราคา สูตร และค่าแรงเปลี่ยนได้ แต่ทุกเวอร์ชันถูกเก็บไว้SCD2 บน DIM_MENU_ITEM, BRG_RECIPE, DIM_STAFF
จัดรูปให้ถามง่ายfact อยู่ตรงกลาง บริบทอยู่รอบ ๆ คำถามกลายเป็น GROUP BY สั้น ๆFCT_* ทุกตัวกับ DIM_* ของมัน
ไม่รบกวนหน้าร้านงานวิเคราะห์หนัก ๆ ไม่ทำให้ POS ช้าในคืนวันศุกร์batch ทุกคืนจาก Raw ไม่ query POS ตรง ๆ

ฐานข้อมูลหน้าร้าน (POS)

  • สร้างมาเพื่อบันทึกออร์เดอร์ทีละใบให้เร็ว
  • normalize แล้ว มีตารางเล็ก ๆ หลายตาราง
  • เก็บสถานะปัจจุบัน แก้ไขทับที่เดิม
  • คนใช้คือแคชเชียร์กับจอในครัว
  • WHERE pos_order_id = 'P-1001'

Warehouse

  • สร้างมาเพื่ออ่านข้อมูลจำนวนมากแล้วตอบคำถาม
  • Star schema: dimension กว้าง fact แคบ
  • เก็บทุกเวอร์ชัน fact เพิ่มอย่างเดียว ไม่แก้
  • คนใช้คือเจ้าของร้าน นักวิเคราะห์ โมเดลพยากรณ์
  • GROUP BY business_date, channel

8 · กฎ 5 ข้อในการออกแบบ fact table

ทุกข้อเป็นการตัดสินใจที่อยู่ใน README อยู่แล้ว ในโน้ตบุ๊กเราตั้งใจทำให้แต่ละข้อพัง เพื่อให้เห็นว่ามันปกป้องอะไรไว้

กฎถ้าฝ่าฝืน…เราใช้ตรงไหน
1 · ตารางละหนึ่ง grain join ออร์เดอร์กับบรรทัดแล้ว sum คอมมิชชัน: คอมมิชชัน Grab วันศุกร์จะเป็น 403.5 แทนที่จะเป็น 257.1 เพราะ GF-201 มีสองบรรทัด FCT_ORDER กับ FCT_ORDER_LINE; ส่วนลดระดับตะกร้าถูกกระจายลงบรรทัด (pro_rata) ไม่ใช่คัดลอก
2 · snapshot ค่าที่เปลี่ยนได้ รายได้ Pepperoni L วันศุกร์: จ่ายจริง 1,037 ถ้าใช้ราคาเมนูวันนี้ได้ 1,047 การขึ้นราคาไปเขียนวันศุกร์ใหม่ ถ้าใช้ราคาตั้งของวันศุกร์ (SCD2) ได้ 987 ส่วนต่าง 50 บาทคือราคาที่ Grab บวกเพิ่ม unit_price_thb, price_delta_thb, unit_cost_thb, ot_multiplier_applied
3 · list ต้องเป็นตาราง ถ้าเก็บ modifier เป็น text ชีสเพิ่มจะไม่ถูกนับเป็นการใช้วัตถุดิบ variance มอซซาเรลลาวันศุกร์จะเป็น −100 กรัม แทนที่จะเป็น −20 กรัม แย่ลงห้าเท่า และผู้จัดการจะไปตามหาคนขโมย FCT_ORDER_LINE_MODIFIER + BRG_MODIFIER_RECIPE; BRG_SUPPLIER_DELIVERY_DAY
4 · รู้ว่าอะไรบวกได้ บวกยอดนับชีสรายวันพฤหัสถึงเสาร์: "เรามีชีส 16.3 กิโล" แต่ในตู้เย็นมี 5.2 กิโล ส่วน AVG(unit_price) ได้ 357.00 แต่ค่าเฉลี่ยจริงคือ 361.86 qty_delta แบบมีเครื่องหมาย (บวกได้) กับ qty_counted (เป็นระดับ); เก็บ regular_hours กับ ot_hours แยกกัน
5 · FK หนึ่งตัวต่อหนึ่งแหล่ง ใช้ source_ref_sk ตัวเดียวร่วมกัน แล้วการรับชีส 2 กิโลไป join เข้ากับพิซซ่าในออร์เดอร์ P-1001 ไม่มี error เลย ได้แค่แถวผิดที่ดูน่าเชื่อ FK สี่ตัวแยกกันใน FCT_INVENTORY_MOVEMENT พร้อม CHECK ว่าตั้งค่าได้อย่างมากหนึ่งตัว
กฎข้อ 2 ในบรรทัดเดียว
snapshot ตอบว่า เกิดอะไรขึ้น ส่วน SCD2 ตอบว่า ตอนนั้นอะไรจริง เราตั้งใจเก็บไว้ทั้งสองแบบ

9 · fact table 4 ประเภท และเราใช้แบบไหน

ประเภทหนึ่งแถวคือ…แถวเปลี่ยนได้ไหม?ของเรา
Transactionหนึ่งเหตุการณ์ ณ เวลาที่เกิดไม่เลยFCT_ORDER_LINE, FCT_PAYMENT, FCT_ORDER_EVENT, FCT_INVENTORY_MOVEMENT, FCT_PURCHASE_ORDER_LINE, FCT_SHIFT
Periodic snapshotสถานะของบางอย่าง ทุกช่วงเวลาไม่เลย เพิ่มแถวใหม่ทุกช่วงFCT_INVENTORY_COUNT (ทุกปิดร้าน)
Accumulating snapshotหนึ่งกระบวนการ หนึ่งคอลัมน์ต่อหนึ่งขั้นได้ อัปเดตเมื่อถึงขั้นถัดไปmart_delivery_sla สร้างจาก FCT_ORDER_EVENT
Factlessบางอย่างเกิดขึ้นหรือเป็นไปได้นาน ๆ ครั้งBRG_CHANNEL_MENU_ITEM ใช้เป็นตาราง coverage
  • เราเก็บ event log แล้วสร้าง accumulating snapshot จากมัน ขั้นใหม่ (เช่น Grab เพิ่ม driver_arrived) เป็นแค่ค่าใหม่ในแถว ไม่ใช่คอลัมน์ใหม่ และ log ไม่ต้องถูกอัปเดตเลย
  • สต็อกคงเหลือคำนวณจาก movement ผลบวกสะสมของ qty_delta ได้ snapshot รายวัน การนับจริงเป็นตัวตรวจ และส่วนต่างระหว่างสองค่าคือ KPI ของเสีย
  • ตาราง coverage หาสิ่งที่ไม่ได้เกิดขึ้น ลงขายลบด้วยขายได้: Pepperoni M ไม่มีออร์เดอร์จาก Grab เลย และฮาวายเอี้ยนขายได้ทางโทรศัพท์แต่ไม่เคยขายได้ที่โต๊ะ fact การขายตัวไหนก็บอกเรื่องนี้ไม่ได้

11 · ตัวอย่างการออกแบบ: fct_forecast

README พูดถึงตาราง forecast แต่ไม่เคยออกแบบ ลองใช้ 4 ขั้นตอนกับของใหม่:

  1. Process โมเดลทำนายความต้องการ การทำนายหนึ่งครั้งคือเหตุการณ์หนึ่ง มีเวลาที่เกิดและมีผลลัพธ์
  2. Grain การพยากรณ์หนึ่งครั้ง ของเมนูหนึ่งรายการ สำหรับวันทำการหนึ่งวัน ในช่องทางหนึ่ง จากการรันโมเดลหนึ่งรอบ รอบการรันต้องอยู่ใน grain เพราะพยากรณ์วันเสาร์ที่ทำวันจันทร์กับที่ทำวันศุกร์เป็นคนละ fact
  3. Dimensions เมนู วันที่ (วันที่ถูกพยากรณ์) และช่องทาง ทั้งสามมีอยู่แล้วสำหรับการขาย เพราะเป็น conformed dimension จึง join ค่าพยากรณ์กับของจริงได้ทันที
  4. Facts forecast_units บวกข้ามเมนู วัน และช่องทางได้ แต่ บวกข้ามรอบไม่ได้ บวกสองรอบของวันเสาร์เดียวกันได้ 7 ถาด แต่รอบล่าสุดบอก 5

12 · สรุป

ทำไปเพื่ออะไร

  • รวมห้าแหล่งให้เป็นรูปแบบเดียว
  • นิยามกฎธุรกิจครั้งเดียว
  • เก็บประวัติที่ POS เขียนทับ
  • จัดรูปข้อมูลให้ถามง่าย
  • ไม่ให้งานวิเคราะห์หนัก ๆ ไปรบกวน POS

ทำออกมายังไง

  • Process → grain → dimension → fact
  • bus matrix ของ conformed dimension
  • surrogate key และ SCD2
  • โหลด fact ด้วยการเปลี่ยน business key เป็น surrogate key ผ่านด่านตรวจคุณภาพ
