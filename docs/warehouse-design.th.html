MADT8102 · Pizza shop · Warehouse specification

Warehouse ของโปรเจกต์: ทีมสร้างอะไร และใช้งานยังไง

warehouse ของโปรเจกต์นี้ ตั้งแต่ข้อมูลต้นทางที่ผ่าน staging แล้ว ไปจนถึง aggregate table ที่เจ้าของร้าน รายการสั่งของ และโมเดลพยากรณ์อ่าน ครอบคลุม dimension, fact table และ data mart ทุกตัว ข้อตกลงเชิง dimensional ที่ทุกตารางต้องทำตาม (MADT8102 บทที่ 5) และการโหลดข้อมูลในแต่ละคืน

สถาปัตยกรรม Kimball dimensional DW โมเดล Star · dimension 16 · fact 13 Data mart 5 · aggregate 6 รอบอัปเดต ทุกคืน 03:00 core · 03:30 aggregate

English version: warehouse-design.html

1 · warehouse คืออะไร และทำไมโปรเจกต์ต้องมี

warehouse คือ zone Trusted และ Refined ของ data lake ของเรา (data-flow.th.html) ในสามสถาปัตยกรรมของบทที่ 5 ของเราคือ Kimball dimensional data warehouse: star schema ชุดเดียวบน conformed dimension ที่ระดับละเอียดที่สุดที่เราได้รับ และนักวิเคราะห์ query ได้โดยตรง data mart คือ subject area ภายใน warehouse (Sales, Delivery, Customer, Inventory and purchasing, Labour) แต่ละตัวมี aggregate table ให้บริการ ที่นี่เป็นที่เดียวที่กฎธุรกิจอยู่ แดชบอร์ด รายการสั่งของ และโมเดลพยากรณ์อ่านจากที่นี่ ไม่อ่านจากระบบต้นทางเลย

เหตุผลเห็นได้ชัดที่สุดจากคำถามเดียว: วันศุกร์ได้รายได้สุทธิแต่ละช่องทางเท่าไร?

ถามจาก source: 30 บรรทัด

query ต้องแบกกฎ 6 ข้อไว้เอง: รวมข้อมูลสองหน้าตา, แปลง UTC เป็นเวลากรุงเทพ, วันทำการ 10:00–02:00, ใช้ MAX ไม่ใช่ SUM กับค่าคอมมิชชันที่ Grab ซ้ำทุกแถว, parse ราคา modifier ออกจาก text และแปลง QR → QR_DINEIN แถม POS ยังเขียนทับราคาของสัปดาห์ก่อนไปแล้วด้วย

ถามจาก warehouse: 7 บรรทัด

SELECT channel_code,
       SUM(net_revenue_thb)
FROM dw.fct_order
JOIN dw.dim_channel USING (channel_key)
JOIN dw.dim_date USING (date_key)
WHERE full_date = '2026-09-04'
GROUP BY channel_code

ได้คำตอบเดียวกัน (Grab 599.9, โทรศัพท์ 408.0, QR 808.0 บาท จากข้อมูลต้นแบบ) กฎทั้งหมดถูกใช้ไปครั้งเดียวตอนโหลด รายงานไหนก็คำนวณผิดไม่ได้

ชั้นเก็บอะไรสร้างเมื่อใครอ่าน

กฎการเข้าถึง

3 · Dimension

dimension ทุกตัวมี surrogate key แบบ _key และ natural key แบบ _nk เก็บ flag เป็นค่าที่อ่านออก ("Weekend" / "Weekday" ไม่ใช่ true / false) เก็บรหัสคู่กับคำอธิบาย และมี special-case row สามแถว: 0 = ไม่เกี่ยวข้อง, 1 = ไม่ทราบ, 2 = ไม่ถูกต้อง fact จึงไม่มี key ที่เป็น NULL เลย

DimensionอธิบายอะไรประวัติHierarchy และหมายเหตุ

6 · ข้อตกลงที่ทุกตารางต้องทำตาม

นี่คือกฎจากบทที่ 5 ที่ทีมใช้กับทุกตารางใหม่ ตัวเลขมาจากต้นแบบใน notebooks/warehouse_design.ipynb ซึ่งตั้งใจทำให้แต่ละข้อพังเพื่อให้เห็นว่ามันปกป้องอะไร

ข้อตกลงปกป้องอะไร (ตัวเลขจากต้นแบบ)
grain ก่อน, drill acrossfact ทุกตัวมี grain ในประโยคเดียว fact ที่ grain ต่างกันอยู่คนละตาราง เทียบ fact สองตัวด้วยการ drill across ไม่ join กันตรง ๆ ถ้า join ออร์เดอร์กับบรรทัด คอมมิชชัน Grab วันศุกร์จะเป็น 403.5 แทน 257.1
ไม่มี key ที่เป็น NULLใช้ special-case row แทน ถ้า customer_key เป็น NULL รายได้ 2,327 จาก 3,782 บาทจะหายไปจากรายงานตามสถานะสมาชิกโดยไม่มี error ถ้าใช้แถว 0 จะแสดงว่า "ไม่เกี่ยวข้อง"
ข้อมูลที่มาช้าต้องถูกโหลดเมนูที่ยังไม่ได้ map ถูกโหลดเข้าแถว 1 "ไม่ทราบ" พร้อมแจ้งเตือน แล้วค่อยชี้ใหม่ทีหลัง ถ้ากักไว้ยอดขายจะต่ำกว่าความจริง
fact ชี้ไปที่ dimensionfact ทุกตัวมี key ไปหาทุก dimension ที่ใช้วิเคราะห์ และไม่มี key ไปหา fact ตัวอื่น การตามย้อนกลับใช้รหัสเอกสารแบบ degenerate ที่ ETL เป็นคนตรวจ
snapshot ค่าที่เป็นนโยบายราคา ต้นทุน และตัวคูณ OT ถูกคัดลอกลง fact ณ ตอนที่เกิด ไม่อย่างนั้นการขึ้นราคาวันเสาร์จะเปลี่ยนรายได้ Pepperoni L วันศุกร์จาก 1,037 เป็น 1,047
list ต้องเป็นตารางห้ามมี list ในคอลัมน์ เก็บ modifier เป็นแถวทำให้ variance มอซซาเรลลาวันศุกร์เป็น −20 กรัม ถ้าเก็บเป็น text จะเป็น −100 กรัม
เก็บสิ่งที่บวกได้measure ที่บวกไม่ได้ต้องแยกเป็นส่วนที่บวกได้ ค่าที่เป็นระดับอย่างยอดนับสต็อกห้ามบวกข้ามเวลา ("คงเหลือ" 16.3 กิโล แต่ของจริง 5.2 กิโล)
junk และ degenerateรหัสและ flag ที่มีค่าไม่กี่แบบไปอยู่ใน junk dimension เหลือไว้ใน fact เฉพาะรหัสธุรกรรมที่เป็น degenerate dimension
ไม่มี snowflakeattribute ที่เกี่ยวข้องกันเก็บไว้ด้วยกันแบบซ้ำซ้อนได้ ETL เป็นคนดูแลความถูกต้องของการอ้างอิง ตำแหน่งงานอยู่ใน DIM_STAFF
วันทำการครั้งเดียวdate_key ถูกกำหนดตอนโหลด (10:00–02:00) query ปลายทางไม่ต้องคำนวณเวลาเองเลย

7 · การโหลดในแต่ละคืน

การตรวจคุณภาพทุกครั้งที่โหลด (รายการเต็มอยู่ใน README §10):

  • คอลัมน์ใน fact ห้ามเป็น NULL business key ที่หา dimension ไม่เจอ (เช่นเมนูใหม่ของ Grab ที่ยังไม่มีใน BRG_CHANNEL_MENU_ITEM) จะถูกโหลดเข้าแถว 1 "ไม่ทราบ" พร้อมแจ้งเตือน แล้วชี้ใหม่เมื่อ map แล้ว รายได้ไม่หายและไม่ต่ำกว่าความจริง
  • ส่วนลดระดับบรรทัดต้องรวมได้เท่ากับส่วนลดระดับออร์เดอร์ทุกใบ ตรวจด้วยการ drill across ผ่าน order_number ข้อนี้ถ้าไม่ผ่านจะหยุดทั้ง batch
  • เอกสารต้นทางของการเคลื่อนไหวสต็อกทุกครั้งต้องมีอยู่จริงใน fact ที่ชนิดเอกสารระบุ และเครื่องหมายของ qty_delta ต้องตรงกับทิศทาง
  • upsert ด้วย (channel_key, order_number) โหลดไฟล์ export ซ้ำก็ไม่ทำให้รายได้เป็นสองเท่า
  • ประมวลผล 3 วันทำการล่าสุดใหม่ทุกคืน เพื่อเก็บออร์เดอร์ที่มาช้า
