Data flow: zone-based lake for the pizza shop

How data gets from the till, the delivery apps and the stock sheets into a weekly report, which data lake pattern we chose from the lecture, and why it fits a one-shop business.

1 · The problem in one paragraph

One pizza shop in Bangkok sells through its own QR menu, by phone, and on four delivery apps (Grab, LINE MAN, ShopeeFood, Robinhood). Each of those systems keeps its own records in its own format. The owner wants to answer questions like which pizzas sell on Friday nights, how much cheese do we need next week, and is labour cost in line with sales. Nobody can answer that from six separate apps. The data has to be brought together in one place, cleaned up, and turned into tables a dashboard can read. That "one place" is the data lake.

2 · Two systems, not one

The most common confusion is between the system that runs the shop and the system that analyses it. They are different things and they run at different speeds.

Operational (runs the shop)

The POS app, the QR menu, Grab's app. A customer taps "order", the kitchen sees it in one second, the receipt prints. This has to be instant and it already is. We do not touch it.

Analytical (this design)

A copy of what already happened, collected from all six systems and reshaped for reports. Nobody is standing at the counter waiting for it. It can run every few minutes or once a night, depending on when someone actually needs the answer.

Does the customer wait 5 minutes?
No. The order goes through the POS instantly, as it does today. "Every 5 minutes" is how often we copy the orders that already finished into the data lake. If the copy job stopped for a day, the shop would keep selling pizza; only the report would be a day behind.

3 · Real time or batch?

The lecture's Lambda pattern exists for cases where someone needs an answer within seconds of the event. So the first question is: who needs what, and by when?

Question the owner asksHow often they lookFreshness needed
What sold last week, by channel and item?Monday morningYesterday's data is fine
How much of each ingredient should we order?Nightly list, checked next morningYesterday's data is fine
How many pizzas will we sell next week?Weekly forecast runYesterday's data is fine
Which customers are drifting away?MonthlyLast month's data is fine
Are delivery apps meeting their SLA?WeeklyYesterday's data is fine

Every question is answered the next morning at the earliest. So the rule we follow is: match the pipeline to the need-by time, not the event time. Orders happen every minute, but the first decision that uses them happens tomorrow. Collect often, process once a night, publish for weekly review. That is batch.

4 · Which pattern from the lecture, and why

The chapter presents eight patterns. Here is how each one fares for a single shop with five data sources.

PatternWhat it isVerdict for us
Mono-zoneOne raw pile, no processing insideToo little. Raw Grab CSVs and POS JSON cannot be joined without a cleaning step.
LambdaBatch layer plus a speed layer for live dataOverkill. No live consumer, and every rule must be coded twice (the slide's own warning).
KappaSpeed layer only, everything is a streamWrong shape. Four of five sources arrive as daily files, not streams.
Data-pondRaw, analog, application, textual, archival pondsBuilt for mixed IoT and text data. We have neither.
Zone-basedLanding → Raw → Trusted → Refined, plus a SandboxChosen. Zones map exactly onto the raw / staging / core / mart layers in our ER model. Each rule written once.
Multi-zone functionalRaw, process, access, govern zonesClose cousin. Adds a govern zone we do not need for one owner and one analyst.
FunctionalIngestion, storage, transformation, interaction layersDescribes the same thing by layer instead of by zone. Fine, but zones are easier to point at in storage.
LakehouseLake storage with warehouse-style tables (Parquet, Delta)Not a rival; it is how we would implement the zones. Raw as Parquet, Trusted and Refined as tables.

6 · Why four zones and not one?

Each zone exists because something goes wrong without it. Read the "without it" column and the design explains itself.

ZoneWhat it holdsWhy it existsWithout it
LandingFiles exactly as they arrived. Deleted after 7 days.A safe drop point. Sources push here without knowing anything about our structure.Grab's export would have to write straight into our tables. One changed column name breaks the load at 06:00 with nobody watching.
RawSame rows, tagged with source, time and file name. Never edited, kept forever.The audit trail and the replay button. Any later bug can be fixed by re-running from here.A bug in the cleaning logic silently corrupts the only copy. You cannot go back.
TrustedOne row per real event, typed, deduplicated, quality-checked, star schema.The single place business rules live: what a "business day" is, which item name means which SKU, what counts as a duplicate.Every dashboard reimplements the rules and they drift. Grab's "Large Pepperoni Pizza" and the POS "PEP-L" are counted as two products.
RefinedOne table per question, pre-aggregated by business day.Dashboards read a small, fast table instead of joining six large ones on every click.The Monday dashboard takes minutes to load and the forecast model queries raw facts.
SandboxScratch copies for experiments. Cleared after 30 days.An analyst can try a new forecast feature without any risk to the reports.Experiments happen in Trusted and one bad UPDATE ruins the week's numbers.

8 · One order, traced

A customer orders a large pepperoni through Grab on Friday evening. This is where that one record is at each point in time.

WhenZoneWhat happens to the order
Fri 19:42—Order placed on Grab. Kitchen gets it instantly through Grab's tablet. Grab's system has the record. We do not yet.
Sat 06:00LandingNightly export from the Grab merchant portal drops orders.csv into landing/grab/2026-09-12/. The order is one line in that file, with Grab's column names and a UTC timestamp.
Sat 06:05RawIngest job copies the file to Parquet and adds source_system = GRAB, ingest_ts, source_file. The line is otherwise untouched. If Grab re-sends the file next week, both copies stay.
Sun 03:00TrustedTransform job runs for business day Friday. The timestamp becomes 19:42 Asia/Bangkok, the row is deduplicated on (GRAB, platform_order_id), "Large Pepperoni Pizza" is mapped to our menu_item_nk, and it becomes one fct_order plus one fct_order_line. A quality gate checks it has a channel, a date and a positive total.
Sun 03:30RefinedAggregate job adds it to mart_sales_daily for Friday × pepperoni × GRAB, and its recipe explosion adds flour, cheese and pepperoni to mart_ingredient_usage_daily.
Mon 09:00ConsumerOwner opens the weekly dashboard. Friday's Grab sales include this order. The reorder list already used its cheese usage on Sunday night.

A dine-in QR order takes the same path but reaches Raw within five minutes instead of the next morning. It still waits for the 03:00 job to become Trusted. That gap is fine, because nothing reads Trusted before then.

10 · When this design would change

  • The owner wants a live "today so far" screen across all channels. Add a speed layer next to the batch path and the design becomes Lambda. The batch side stays exactly as it is.
  • A second branch opens. Add a store dimension and partition Raw by store. The zones do not change.
  • A delivery app offers a real-time API instead of daily CSV. Collect it every 5 minutes like POS. Still lands in Landing, still processed nightly.
The one-line summary
Collect often, keep everything raw, clean once, aggregate once, read many times. Batch is not a compromise here; it is the right speed for every question on the list.
