MADT8102 · Pizza shop · Minimal warehouse

Warehouse เวอร์ชันย่อ: ยอดขายระดับบรรทัด ตัวเลือกจากรายการ แดชบอร์ดเดียว

ขอบเขตที่ตกลงกับอาจารย์ไว้ ปรับหลังรีวิวรอบที่สอง: ออร์เดอร์คือ header บรรทัดคือ body fact อยู่ระดับบรรทัด และ modifier คือตัวเลือกที่กดจากรายการ สร้างครบทั้งเส้นเพื่อให้เจ้าของร้านเห็นรายได้ตามช่องทาง เมนูที่ขายดี และรายได้จากของเพิ่ม (add-on) ทุกตัวเลขในหน้านี้มาจาก notebooks/warehouse_minimal.ipynb

Fact 2 ตัว ระดับบรรทัด Dimension 6 ตัว + bridge 1 ตัว Aggregate 3 ตัว ผู้ใช้ แดชบอร์ดเจ้าของร้าน

1 · ขอบเขต

อยู่ในขอบเขต

  • แหล่งข้อมูลการขายสองแหล่ง: POS (QR, โทรศัพท์) และไฟล์ export ของแอปเดลิเวอรี
  • conformed dimension หกตัวและ bridge หนึ่งตัว
  • fact สองตัวระดับบรรทัด: FCT_ORDER_LINE และ FCT_ORDER_LINE_OPTION
  • aggregate table สามตัว
  • ผู้ใช้กลุ่มเดียว: แดชบอร์ดของเจ้าของร้าน

ยังไม่อยู่ในขอบเขต

  • สต็อก การสั่งของ และการสั่งซื้อ
  • กะงานและค่าแรง
  • การชำระเงินและโปรโมชัน
  • เวลาการจัดส่ง
  • โมเดลพยากรณ์และการแบ่งกลุ่มลูกค้า

ขอบเขตเล็กลงแต่กฎการออกแบบไม่เปลี่ยน ยังเป็น Kimball dimensional warehouse ตาม MADT8102 บทที่ 5: surrogate key แบบ _key, special-case row (0 ไม่เกี่ยวข้อง, 1 ไม่ทราบ, 2 ไม่ถูกต้อง) แทน key ที่เป็น NULL, junk dimension สำหรับสถานะออร์เดอร์, เลขออร์เดอร์และเลขบรรทัดเป็น degenerate dimension และเทียบ fact ด้วยการ drill across

4 · Header และ body: fact อยู่ระดับบรรทัด

POS และแอปเดลิเวอรีทุกเจ้าส่งออร์เดอร์มาเป็น header (ใคร เมื่อไร ช่องทางไหน ค่าคอมมิชชัน ค่าส่ง) และ บรรทัด หนึ่งบรรทัดต่อเมนูหนึ่งรายการ warehouse เก็บ fact การขายตัวเดียวที่ระดับบรรทัด:

  • attribute ของ header กลายเป็น key บนทุกบรรทัด วันที่ ช่องทาง ลูกค้า และสถานะออร์เดอร์เหมือนกันทุกบรรทัดของออร์เดอร์ ทุกบรรทัดจึงมี key เหล่านี้
  • เงินของ header ถูกกระจายลงมา ค่าคอมมิชชันและค่าส่งถูกแบ่งให้บรรทัดตามสัดส่วนยอดขายของบรรทัด (ราคาเมนูบวกตัวเลือก) ปัดเป็นสตางค์ และเศษไปไว้ที่บรรทัดสุดท้าย เช่น GF-201 ค่าคอมมิชชัน 146.4 บาทกลายเป็น 113.70 บนเปปเปอโรนี 379 บาท และ 32.70 บนขนมปังกระเทียม 109 บาท
  • ตัว header เองคือ order_number แบบ degenerate จำนวนออร์เดอร์คือ COUNT(DISTINCT order_number)
  • กระทบยอดทุกครั้งที่โหลด ค่าคอมมิชชันที่กระจายแล้วรวมตามออร์เดอร์ต้องเท่ากับของ header ไม่อย่างนั้นการโหลดจะหยุด

measure การขายทุกตัวอยู่ที่ grain เดียว รายได้ ค่าคอมมิชชัน และรายได้สุทธิจึงรวมได้แบบเดียวกันทั้งตามออร์เดอร์ ช่องทาง วัน หรือเมนู ไม่ต้อง join กับ fact ของ header และไม่มีอะไรถูกนับซ้ำ

ตัวเลือกมาจากการกดเลือก ไม่ใช่การพิมพ์

หน้าจอ POS แสดงตัวเลือกของแต่ละเมนูจาก DIM_MODIFIER_OPTION (จัดกลุ่มเป็น ชีส ความเผ็ด แป้ง) และบันทึกทุกการกดเป็นแถว: ออร์เดอร์ บรรทัด รหัสตัวเลือก ราคาที่คิด ไม่มีข้อความอิสระเข้ามาใน warehouse เลย รหัสที่ไม่อยู่ในรายการจะถูกโหลดเข้าแถว 2 Invalid พร้อมแจ้งเตือน จึงมองเห็นได้และไม่หายไป
